## `/office-hours`

這是每個專案都應該開始的地方。

在你計劃、審核或寫代碼之前 —— 與一位 YC 風格的合夥人坐下來，思考你實際正在構建的是什麼。不是你「以為」你在構建的內容，而是你「實際」在構建的東西。

### 重新定義 (The reframe)

這是一個真實專案中發生的情況。用戶說：「我想為我的日曆建立一個每日簡報應用程式。」合理的請求。接著技能詢問了痛點 —— 具體的例子，而非假設。用戶描述了秘書遺漏事項、多個 Google 帳號中的日曆項資訊過時、準備文件滿是 AI 粗糙內容、活動地點錯誤且花費太長時間追蹤等問題。

技能的回覆是：*「我要反對這個定義，因為我認為你已經超出了它的範疇。你說的是『用於多 Google 日曆管理的每日簡報應用程式』。但你實際描述的是一個個人幕僚長 (Chief of Staff) AI。」*

接著它提取了五個用戶沒意識到自己正在描述的能力：

1. **監控你的日曆**：跨所有帳號並偵測過時資訊、缺失的地點、權限缺口。
2. **生成真正的準備工作**：不是物流摘要，而是為了董事會會議、播客或募款活動準備的 *智力工作*。
3. **管理你的 CRM**：你要見誰、關係如何、他們想要什麼、歷史記錄為何。
4. **安排時間優先級**：標記何時需要提前開始準備、主動預留時間、按重要性對活動進行排名。
5. **用金錢換取槓桿**：主動尋找委派或自動化的方式。

這次重新定義改變了整個專案。他們原本打算構建一個日曆應用程式，現在他們正在構建價值高出十倍的東西 —— 因為這項技能傾聽的是他們的痛點，而不是他們的功能需求。

### 挑戰前提 (Premise challenge)

在重新定義之後，它會提出前提讓你驗證。不是問「這聽起來好嗎？」，而是關於產品的實際可證偽主張：

1. 日曆是核心數據源，但價值在於其上的智慧層。
2. 助理不會被取代 —— 他們會被賦予超能力。
3. 最核心的小功能 (narrowest wedge) 是一個真正起作用的每日簡報。
4. CRM 整合是必須具備的 (must-have)，而非可有可無 (nice-to-have)。

你同意、反對或調整。你接受的每個前提都會成為設計文件中承重的一部分。

### 替代實作方案 (Implementation alternatives)

接著它會生成 2-3 個具體的實作方案，並附帶誠實的工作量估算：

- **方案 A：每日簡報優先** — 最核心的小功能，明天交付，中等 (M) 工作量 (人類: ~3 週 / CC: ~2 天)
- **方案 B：CRM 優先** — 先構建關係圖譜，較大 (L) 工作量 (人類: ~6 週 / CC: ~4 天)
- **方案 C：完整願景** — 一次完成所有功能，超大 (XL) 工作量 (人類: ~3 個月 / CC: ~1.5 週)

建議選擇 A，因為你可以從實際使用中學習。CRM 數據會在第二週自然產生。

### 兩種模式

**創業模式 (Startup mode)** — 適用於正在創業的創辦人和內部創業者。你會獲得從 YC 合夥人如何評估產品中提煉出的六個強迫性問題：需求現實、現狀、極具針對性的具體細節、最核心的小功能、觀察與驚喜，以及未來契合度。這些問題是故意讓人感到不舒服的。如果你無法點名需要你產品的具體個人，那是你在寫任何代碼前最需要弄清楚的事。

**開發者模式 (Builder mode)** — 適用於黑客松、側邊專案、開源、學習和純樂趣。你會得到一位熱情的協作者，協助你找到想法的最酷版本。什麼會讓某人驚嘆「喔！」？通往你可以分享的東西的最快路徑是什麼？這些問題是生成式的，而非質詢式的。

### 設計文件

兩種模式都會以寫入 `~/.gstack/projects/` 的設計文件結束 —— 且該文件直接餵入 `/plan-ceo-review` 和 `/plan-eng-review`。完整的生命週期現在是：`office-hours → 計劃 → 實作 → 審核 → QA → 交付 → 回顧`。

在設計文件獲得批准後，`/office-hours` 會反映它注意到的關於你思考方式的內容 —— 不是泛泛的表揚，而是對你在對話中所說內容的具體回應。這些觀察也會出現在設計文件中，以便你稍後閱讀時再次看到。

## `/plan-ceo-review`

這是我的 **創辦人模式**。

這是我希望模型展現品味、抱負、用戶同理心和長線思維的地方。我不希望它照本宣科地接受請求。我希望它先問一個更重要的問題：

**這個產品到底是用來做什麼的？**

我將這視為 **Brian Chesky 模式**。

重點不是去完成那個顯而易見的任務。重點是從用戶的角度重新思考問題，並找到那個感覺是必然的、令人愉悅的、甚至帶有一點魔力的版本。

### 範例

假設我正在構建一個類似 Craigslist 的列表應用程式，我說：

> 「讓賣家為他們的物品上傳照片。」

一個平庸的助手會增加一個檔案選擇器並儲存一張圖片。

那不是真正的產品。

在 `/plan-ceo-review` 中，我希望模型詢問「上傳照片」是否真的是這項功能。也許真正的功能是協助某人建立一個真正能賣出去的列表。

如果那是真正的任務，整個計劃就會改變。

現在模型應該詢問：

* 我們能從照片中識別出產品嗎？
* 我們能推斷出 SKU 或型號嗎？
* 我們能搜尋網路並自動起草標題和描述嗎？
* 我們能擷取規格、分類和定價參考嗎？
* 我們能建議哪張照片最適合做為封面圖來提高轉化率嗎？
* 我們能偵測上傳的照片是否醜陋、昏暗、凌亂或信任度低嗎？
* 我們能讓這種體驗感覺是高端的，而不是像 2007 年那種死氣沉沉的表單嗎？

這就是 `/plan-ceo-review` 為我做的。

它不只是問：「我如何增加這項功能？」
它問的是：**「隱藏在這個請求中的十星級產品是什麼？」**

### 四種模式

- **範疇擴張 (SCOPE EXPANSION)** — 大膽夢想。代理會提出雄心勃勃的版本。每次擴張都會作為一個你選擇加入的獨立決策呈現。熱情推薦。
- **選擇性擴張 (SELECTIVE EXPANSION)** — 將當前範疇作為基準，但看看還有什麼可能。代理會逐一呈現擴張機會並給予中性建議 —— 你挑選值得做的那些。
- **維持範疇 (HOLD SCOPE)** — 對現有計劃進行最嚴格的審查。不提出任何擴張建議。
- **範疇縮減 (SCOPE REDUCTION)** — 尋找最小可行版本。砍掉其餘一切。

願景與決策會持久化到 `~/.gstack/projects/`，以便在對話結束後仍能保留。卓越的願景可以被提升到你倉庫中的 `docs/designs/` 供團隊參閱。

## `/plan-eng-review`

這是我的 **工程經理模式**。

一旦產品方向正確，我想要的是完全不同類型的智慧。我不再需要更多發散的創意。我不再需要更多「如果...不是很酷嗎」。我希望模型成為我最好的技術主管。

這個模式應該搞定：

* 架構
* 系統邊界
* 資料流
* 狀態轉移
* 失敗模式
* 邊際情況
* 信任邊界
* 測試覆蓋率

還有一個對我來說非常驚人的解鎖：**圖表**。

當你強迫 LLM 繪製系統時，它們會變得更加完整。時序圖、狀態圖、組件圖、資料流圖，甚至測試矩陣。圖表強迫隱藏的假設浮出水面。它們讓敷衍的計劃變得更加困難。

所以 `/plan-eng-review` 是我希望模型構建能支撐起產品願景的技術骨幹的地方。

### 範例

以同樣的列表應用程式為例。

假設 `/plan-ceo-review` 已經完成了它的工作。我們決定真正的功能不只是照片上傳。它是一個智慧列表流程，能夠：

* 上傳照片
* 識別產品
* 從網路豐富列表內容
* 起草強大的標題和描述
* 建議最佳封面圖

現在由 `/plan-eng-review` 接手。

現在我希望模型回答以下問題：

* 上傳、分類、內容豐富和草稿生成的架構是什麼？
* 哪些步驟是同步發生的，哪些進入背景任務？
* 應用伺服器、物件儲存、視覺模型、搜尋/內容豐富 API 以及列表資料庫之間的邊界在哪裡？
* 如果上傳成功但內容豐富失敗會發生什麼？
* 如果產品識別信心度低會發生什麼？
* 重試機制如何運作？
* 我們如何防止重複任務？
* 什麼時候持久化什麼內容，哪些可以安全地重新計算？

這就是我需要圖表的地方 —— 架構圖、狀態模型、資料流圖、測試矩陣。圖表強迫隱藏的假設浮出水面。它們讓敷衍的計劃變得更加困難。

這就是 `/plan-eng-review`。

不是「把想法變小」。
**是讓想法變得可構建。**

### 審核就緒儀表板 (Review Readiness Dashboard)

每次審核（CEO、工程、設計）都會記錄其結果。在每次審核結束時，你會看到一個儀表板：

```
+====================================================================+
|                    審核就緒儀表板 (REVIEW READINESS)                 |
+====================================================================+
| 審核項目        | 次數 | 最後執行時間        | 狀態      | 必要項   |
|-----------------|------|---------------------|-----------|----------|
| 工程審核 (Eng)  |  1   | 2026-03-16 15:00    | 通過      | 是       |
| CEO 審核        |  1   | 2026-03-16 14:30    | 通過      | 否       |
| 設計審核        |  0   | —                   | —         | 否       |
+--------------------------------------------------------------------+
| 判定：准予交付 — 工程審核已通過                                      |
+====================================================================+
```

工程審核是唯一的必要門檻（可透過 `gstack-config set skip_eng_review true` 停用）。CEO 與設計審核僅供參考 —— 分別針對產品和 UI 變更進行建議。

### 計劃到 QA 流程 (Plan-to-QA flow)

當 `/plan-eng-review` 完成測試審核章節時，它會將測試計劃產物寫入 `~/.gstack/projects/`。當你稍後執行 `/qa` 時，它會自動讀取該測試計劃 —— 你的工程審核直接餵入 QA 測試，無需手動複製貼上。

## `/plan-design-review`

這是我的 **資深設計師在審核你的計劃** —— 在你寫下任何一行代碼之前。

大多數計劃描述了後端做什麼，但從不指明用戶實際看到了什麼。空白狀態？錯誤狀態？載入狀態？行動版佈局？AI 粗糙感 (Slop) 的風險？這些決定被延後到「在實作過程中解決」 —— 然後工程師交付了「找不到項目。」作為空白狀態，因為沒人指明更好的方案。

`/plan-design-review` 在計劃階段就捕捉到這一切，此時修復成本最低。

它的運作方式與 `/plan-ceo-review` 和 `/plan-eng-review` 類似 —— 互動式、每次處理一個問題，並採用 **停止 + AskUserQuestion** 模式。它為每個設計維度評分 0-10，說明 10 分的樣子，然後編輯計劃以達成目標。評分驅動工作：評分低 = 大量修復，評分高 = 快速通過。

對計劃進行七輪審查：資訊架構、互動狀態覆蓋、用戶旅程、AI 粗糙風險、設計系統一致性、響應式/無障礙，以及未解決的設計決策。在每一輪中，它會發現缺口並直接修復它們（明顯的缺口）或要求你做出設計選擇（真正的權衡）。

### 範例

```
你：   /plan-design-review

Claude: 初始設計評分：4/10

        「這個計劃描述了一個用戶儀表板，但從未指明
         用戶首先看到什麼。它說『帶有圖示的卡片』 ——
         這看起來像每個 SaaS 模板。它提到了零個
         載入狀態、零個空白狀態，且沒有行動版行為。」

        第一輪 (資訊架構)：3/10
        「10 分的定義是為每個螢幕定義主要/次要/三級內容的層級。」
        → 在計劃中新增了資訊層級章節

        第二輪 (互動狀態)：2/10
        「計劃有 4 個 UI 功能，但 20 個互動狀態中
         指明了 0 個 (4 個功能 × 5 個狀態)。」
        → 在計劃中新增了互動狀態表

        第四輪 (AI 粗糙感)：4/10
        「計劃中說『帶有卡片和圖示的簡潔現代 UI』
         以及『帶有漸層的英雄章節』。這是前兩名
         最像 AI 生成的模式。」
        → 用具體、有意的替代方案重寫了 UI 描述

        總體：4/10 → 修復後為 8/10
        「計劃已完成設計規範。實作後請執行 /design-review 進行視覺 QA。」
```

當你重新執行時，已經在 8 分以上的章節會快速通過。低於 8 分的章節會獲得完整處理。對於實作後的直播網站視覺審計，請使用 `/design-review`。

## `/design-consultation`

這是我的 **設計合夥人模式**。

`/plan-design-review` 審核已存在的網站。`/design-consultation` 適用於當你還一無所有時 —— 沒有設計系統、沒有字體選擇、沒有調色盤。你正從零開始，希望有一位資深設計師與你坐下來，共同構建整個視覺識別系統。

這是一場對話，而不是一份表單。代理會詢問你的產品、用戶和受眾。它會思考你的產品需要傳達什麼 —— 信任、速度、工藝、溫暖，或任何適合的特質 —— 並從中推導出具體的選擇。接著它會提出一個完整、連貫的設計系統：美學方向、排版（3 種以上具有特定角色的字體）、帶有十六進位值的調色盤、間距比例、佈局方法以及動態策略。每項建議都附帶理由。每個選擇都強化了所有其他選擇。

但連貫性只是基本門檻。每個開發工具儀表板看起來都一樣 —— 簡潔的無襯線字體、柔和的灰色、藍色點綴。它們都很連貫，但也都很容易被遺忘。看起來「漂亮」的產品與讓人「過目不忘」的產品之間的區別在於 **刻意的創意冒險**：出人意料的標題襯線字體、在你的類別中沒人使用的粗放點綴色、讓你的數據感覺權威而非空洞的緊湊間距。

這才是 `/design-consultation` 的真正意義。它不只是提出一個安全的系統。它提出安全選擇「以及」冒險 —— 並告訴你哪個是哪個。「這裡有些選擇能讓你在你的類別中具備專業度。而這裡是我認為你應該打破慣例的地方，以及原因。」你挑選要冒哪些險。代理會檢查無論哪種方式，整個系統是否仍保持連貫。

如果你願意，代理會研究你領域中已有的產品 —— 擷取真實網站的截圖，分析它們的字體、顏色和間距 —— 這樣你在做選擇前就能看到市場景觀。這不是為了抄襲，而是為了進入正確的範圍以便了解慣例，然後決定哪些值得打破。

在你同意該系統後，它會生成一個互動式 HTML 預覽頁面 —— 不只是色塊和字體樣本，而是真實的產品頁面。如果你正在構建儀表板，你會看到一個帶有側邊欄、數據表和統計卡片的儀表板。如果你正在構建營銷網站，你會看到一個帶有真實文案和行動呼籲 (CTA) 的英雄章節。一切都以你的設計系統渲染，使用你的產品名稱，並提供亮色和深色模式。在寫下任何一行生產代碼前，你就能感受到你的產品會是什麼樣子。

然後它會將 `DESIGN.md` 寫入你的倉庫根目錄 —— 作為你專案設計的唯一事實來源 —— 並更新 `CLAUDE.md`，以便未來所有的 Claude Code 會話都遵循該系統。從那時起，`/design-review` 就可以對照它進行審計，任何處理你前端的代理都會知道規則。

### 範例

```

Claude: 從 README 來看，這似乎是一個針對工程團隊的
        開發者分析儀表板。對嗎？告訴我你想要的感覺 ——
        你希望我先看看現有的產品以便了解景觀嗎？

Claude: [瀏覽 Linear, Vercel, Datadog, Posthog — 擷取截圖]

        和柔和的藍灰色調。Linear 以深色優先和緊湊間距脫穎而出。

        自身特色的地方。哪些冒險吸引你？

## `/design-review`

這是我的 **會寫代碼的設計師模式**。

`/plan-design-review` 在實作前審核你的計劃。`/design-review` 則在實作後審核並修復直播網站。

它在你的直播網站上執行 80 項視覺審計，然後進入修復循環：針對每項設計發現，它會定位源檔案，進行最小限度的 CSS/樣式更改，以 `style(design): FINDING-NNN` 提交，重新導航以驗證，並擷取修復前後的截圖。每次修復一個提交，完全可細分。

其自我監控啟啟發式方法專為設計工作調整 —— 僅限 CSS 的變更會獲得通行（它們本質上是安全且可逆的），但對組件 JSX/TSX 檔案的更改則會計入風險預算。硬性上限為 30 次修復。如果風險分數超過 20%，它會停止並詢問。

### 範例

```
你：   /design-review https://myapp.com

Claude: [在直播網站上執行完整的 80 項視覺審計]
        設計評分：C  |  AI 粗糙評分：D
        12 項發現 (4 項高、5 項中、3 項磨光)

        正在修復 9 個設計問題...

        style(design): FINDING-001 — 將 3 欄圖示網格替換為不對稱佈局
        style(design): FINDING-002 — 增加標題比例 48/32/24/18/16
        style(design): FINDING-003 — 移除漸層英雄章節，改用粗體排版
        style(design): FINDING-004 — 為標題增加第二種字體
        style(design): FINDING-005 — 根據元素角色變化邊框半徑
        style(design): FINDING-006 — 正文左對齊，保留中心位置給標題
        style(design): FINDING-007 — 為所有互動元素增加懸停/焦點狀態
        style(design): FINDING-008 — 增加 prefers-reduced-motion 媒體查詢
        style(design): FINDING-009 — 正文最大內容寬度設置為 680px

        最終審計：
        設計評分：C → B+  |  AI 粗糙評分：D → A
        已套用 9 次修復 (8 次已驗證, 1 次盡力而為)。3 次延後。

        [帶有前後截圖的報告已儲存至 .gstack/design-reports/]
```

九個提交，每個只觸及一個關注點。AI 粗糙評分從 D 升至 A，因為三個最顯眼的模式（漸層英雄章節、3 欄網格、統一半徑）都消失了。

## `/review`

這是我的 **偏執資深工程師模式**。

測試通過並不意味著分支是安全的。

`/review` 存在的原因是有一整類 Bug 可以逃過 CI 的法眼，然後在生產環境中讓你措手不及。這個模式不是為了更大膽的夢想，也不是為了讓計劃更漂亮。它是為了詢問：

**還有什麼會壞掉？**

這是一次結構性審計，而不是風格上的挑刺。我希望模型尋找以下內容：

* N+1 查詢
* 過時讀取 (stale reads)
* 競態條件 (race conditions)
* 糟糕的信任邊界
* 缺失的索引
* 轉義 (escaping) Bug
* 遭到破壞的不變量 (invariants)
* 糟糕的重試邏輯
* 雖然通過但遺漏了真實失敗模式的測試
* 被遺忘的列舉 (Enum) 處理程序 —— 增加一個新的狀態或類型常量，`/review` 會在你的整個代碼庫中追蹤它，包含每個 switch 語句和允許列表，而不僅僅是你更改的檔案。

### 優先修復 (Fix-First)

發現的問題會被處理，而不僅僅是列出。明顯的機械式修復（死代碼、過時註釋、N+1 查詢）會自動執行 —— 你會看到每個問題對應的 `[自動修復] 檔案:行 問題 → 執行了什麼`。真正模糊的問題（安全性、競態條件、設計決策）會浮現供你裁決。

### 完整性缺口

`/review` 現在會標記那些完整版本成本低於 30 分鐘 CC 時間的捷徑實作。如果你選擇了 80% 的解決方案，而 100% 的解決方案是「湖泊」而非「海洋」，審核會將其指出。

### 範例

假設智慧列表流程已實作且測試為綠色。

`/review` 仍應詢問：

* 在渲染列表照片或草稿建議時，我是否引入了 N+1 查詢？
* 我是在信任客戶端提供的檔案元數據，還是有驗證實際檔案？
* 兩個分頁是否會發生競爭並覆蓋封面圖選擇或項目詳情？
* 上傳失敗是否會在儲存空間中永久留下孤兒檔案？
* 「精確的一張封面圖」規則在並發情況下會被破壞嗎？
* 如果內容豐富 API 部分失敗，我是優雅降級還是儲存垃圾數據？
* 我是否在將網路數據引入草稿生成時，意外建立了提示詞注入或信任邊界問題？

這就是 `/review` 的意義。

我在這裡不需要奉承。
我需要模型在生產事故發生前就預見到它。

## `/investigate`

當有東西壞了而你不知道原因時，`/investigate` 是你的系統化除錯器。它遵循鐵律：**在修復之前必須先進行根因調查。**

它不靠猜測和修補，而是追蹤資料流、匹配已知 Bug 模式，並一次測試一個假設。如果三次修復嘗試都失敗，它會停止並質疑架構，而不是胡亂嘗試。這防止了「讓我再試一件事」這種浪費數小時的惡性循環。

## `/qa`

這是我的 **QA 負責人模式**。

`/browse` 給予代理雙眼。`/qa` 則給予它一套測試方法論。

最常見的使用場景：你正在功能分支上，剛剛完成代碼，想要驗證一切正常。只需說 `/qa` —— 它會讀取你的 git 差異、識別你的變更影響了哪些頁面和路由、啟動瀏覽器並測試每一項。無需提供 URL，無需手動編寫測試計劃。

四種模式：

- **差異感知 (Diff-aware)**（在功能分支上自動執行）— 讀取 `git diff main`，識別受影響的頁面，並針對性地進行測試。
- **完整模式 (Full)** — 對整個應用程式進行系統性探索。耗時 5-15 分鐘。記錄 5-10 個證據充足的問題。
- **快速模式 (Quick)** (`--quick`) — 30 秒冒煙測試。測試首頁 + 前 5 個導航目標。
- **回歸模式 (Regression)** (`--regression baseline.json`) — 執行完整模式，然後與先前的基準進行比對。

### 自動回歸測試

當 `/qa` 修復一個 Bug 並驗證後，它會自動生成一個回歸測試，捕捉出錯的確切情境。測試包含追溯到 QA 報告的完整歸因。

### 範例

```
你：   /qa https://staging.myapp.com

Claude: [探索了 12 個頁面，填寫了 3 個表單，測試了 2 個流程]

        QA 報告：staging.myapp.com — 健康評分：72/100

        前 3 大問題：
        1. 關鍵：結帳表單在必填欄位為空時仍可提交
        2. 高：行動版導航選單在選擇項目後不會關閉
        3. 中：儀表板圖表在 1024px 以下會與側邊欄重疊

        [完整報告與截圖已儲存至 .gstack/qa-reports/]
```

**測試需要身份驗證的頁面**：先使用 `/setup-browser-cookies` 匯入你真實瀏覽器的會話，然後 `/qa` 即可測試登入後的頁面。

## `/ship`

這是我的 **發布機器模式**。

一旦我決定了要構建什麼、敲定了技術計劃並執行了嚴格的審核，我不再需要更多討論。我需要執行。

`/ship` 用於最後一哩路。它適用於已經準備好的分支，而不是用來決定構建什麼。

這是模型應該停止扮演腦力激盪夥伴，開始表現得像一名紀律嚴明的發布工程師的地方：與 main 分步同步、執行正確的測試、確保分支狀態健全、如果倉庫有要求則更新更新日誌或版本號、推送，並建立或更新 PR。

### 測試引導 (Test bootstrap)

如果你的專案沒有測試框架，`/ship` 會幫你設置一個 —— 偵測你的運行環境、研究最佳框架、安裝它、為你的實際代碼撰寫 3-5 個真實測試、設置 CI/CD (GitHub Actions)，並建立 TESTING.md。100% 測試覆蓋率是目標 —— 測試讓「憑感覺編程」變得安全，而不是「放手一搏」。

### 覆蓋率審核 (Coverage audit)

每次 `/ship` 執行都會從你的差異中構建代碼路徑地圖、搜尋對應的測試，並產出帶有品質星級的 ASCII 覆蓋率圖表。缺口會自動生成測試。你的 PR 主體會顯示覆蓋率變動：`測試：42 → 47 (+5 個新測試)`。

### 審核門檻 (Review gate)

`/ship` 在建立 PR 前會檢查 [審核就緒儀表板](#review-readiness-dashboard)。如果缺失工程審核，它會詢問 —— 但不會阻擋你。決定會按分支儲存，因此你永遠不會被重複詢問。

很多分支在有趣的工作完成後就夭折了，只剩下無聊的發布工作。人類會拖延那部分，AI 不應該。

## `/document-release`

這是我的 **技術文件撰寫員模式**。

在 `/ship` 建立 PR 之後但在合併之前，`/document-release` 會讀取專案中的每個文件檔案，並與差異進行交叉比對。它會更新檔案路徑、指令清單、專案結構樹以及任何產生偏差的內容。風險變更或主觀變更會作為問題浮現 —— 其餘一切均為自動處理。

```
你：   /document-release

Claude: 正在分析 3 個提交中變更的 21 個檔案。發現 8 個文件檔案。

        README.md：將技能數量從 9 更新為 10，並在表格中新增了新技能
        CLAUDE.md：在專案結構中新增了新目錄
        CONTRIBUTING.md：最新版本 — 無需變更
        TODOS.md：標記 2 個項目為已完成，新增了 1 個新項目

        所有文件已更新並提交。PR 主體已更新文件差異。
```

它還會修飾更新日誌 (CHANGELOG) 的語氣（絕不會覆蓋已有記錄）、清理已完成的待辦事項 (TODOS)、檢查跨文件的一致性，並僅在適當的時候詢問版本 (VERSION) 提升。

## `/retro`

這是我的 **工程經理模式**。

在週末，我想知道實際發生了什麼。不是感覺 —— 是數據。`/retro` 分析提交歷史、工作模式和發布速度，並撰寫一份坦誠的回顧。

它具備團隊意識。它會識別是誰在執行指令，為你自己的工作提供最深度的分析，然後為每位貢獻者提供具體的表揚與成長機會。它會計算指標，如提交數、LOC（代碼行數）、測試比例、PR 大小和修復比例。它從提交時間戳中偵測編程會話、尋找熱點檔案、追蹤發布連勝紀錄，並識別本週最大的交付內容。

它還會追蹤測試健康度：總測試檔案、此期間新增的測試、回歸測試提交以及趨勢變化。如果測試比例低於 20%，它會將其標記為成長領域。

### 範例

```
你：   /retro

Claude: 3 月 1 日當週：47 次提交 (3 位貢獻者), 3.2k LOC, 38% 測試, 12 個 PR, 高峰：晚上 10 點 | 連勝：47 天

        ## 你的本週回顧
        32 次提交, +2.4k LOC, 41% 測試。高峰時段：晚上 9-11 點。

## `/browse`

這是我的 **QA 工程師模式**。

`/browse` 是閉合循環的技能。在此之前，代理可以思考和編寫代碼，但仍處於半盲狀態。它必須猜測 UI 狀態、驗證流程、重導向、控制台錯誤、空白狀態和損壞的佈局。現在它只需去看一眼即可。

它是一個編譯後的二進位檔，與持久化的 Chromium 守護進程通訊 —— 基於微軟的 [Playwright](https://playwright.dev/)。第一次調用啟動瀏覽器（約 3 秒），之後每次調用：約 100-200 毫秒。瀏覽器在指令之間保持運行，因此 Cookie、分頁和 localStorage 都會保留。

### 範例

```
你：   /browse staging.myapp.com — 登入、測試註冊流程，
       並檢查我在這個分支中更改的每個頁面

Claude: [18 次工具調用, ~60 秒]

        > browse goto https://staging.myapp.com/signup
        > browse snapshot -i
        > browse fill @e2 "test@example.com"
        > browse fill @e3 "password123"
        > browse click @e5                    (提交)
        > browse screenshot /tmp/signup.png
        > Read /tmp/signup.png

        註冊成功。重導向至引導流程。現在檢查已變更的頁面。

        > browse goto https://staging.myapp.com/dashboard
        > browse screenshot /tmp/dashboard.png
        > Read /tmp/dashboard.png
        > browse console

        儀表板載入。無控制台錯誤。圖表以範例數據渲染。

        所有 4 個頁面載入正確。無控制台錯誤。無佈局損壞。
        註冊 → 引導 → 儀表板流程端到端正常運作。
```

18 次工具調用，約一分鐘。完整的 QA 通過。無需開啟瀏覽器。

### 瀏覽器接手 (Browser handoff)

當無頭瀏覽器卡住時 —— 驗證碼 (CAPTCHA)、多重驗證 (MFA)、複雜身份驗證 —— 移交給用戶：

```
Claude: 我在登入頁面卡在驗證碼上了。正在開啟一個可見的
        Chrome 供你解決。

        > browse handoff "在登入頁面卡在驗證碼"

        Chrome 已開啟於 https://app.example.com/login 並保留了你所有的
        Cookie 和分頁。解決驗證碼後告訴我你完成了。

你：    完成了

Claude: > browse resume

        獲取了新鮮的快照。成功登入。繼續 QA。
```

瀏覽器在接手過程中保留所有狀態 (Cookie、localStorage、分頁)。在 `resume` 後，代理會從你中斷的地方獲取新鮮的快照。如果瀏覽工具連續失敗 3 次，它會自動建議使用 `handoff`。

**安全性說明**：`/browse` 運行一個持久化的 Chromium 會話。Cookie、localStorage 和會話狀態會在指令之間保留。除非你有意為之，否則請勿針對敏感的生產環境使用它 —— 它是一個具有真實狀態的真實瀏覽器。會話在閒置 30 分鐘後會自動關閉。

如需完整指令參考，請參閱 [BROWSER_zh_TW.md](../BROWSER_zh_TW.md)。

## `/setup-browser-cookies`

這是我的 **會話管理員模式**。

在 `/qa` 或 `/browse` 能夠測試需要身份驗證的頁面前，它們需要 Cookie。與其每次都要手動透過無頭瀏覽器登入，`/setup-browser-cookies` 會直接從你日常使用的瀏覽器匯入真實會話。

它會自動偵測已安裝的 Chromium 瀏覽器（Comet, Chrome, Arc, Brave, Edge），透過 macOS 金鑰鏈 (Keychain) 解密 Cookie，並將其載入 Playwright 會話中。互動式選擇器 UI 讓你精確選擇要匯入哪些域名 —— 絕不會顯示 Cookie 值。

```
你：   /setup-browser-cookies

Claude: Cookie 選擇器已開啟 — 請在瀏覽器中選擇你想要匯入的
        域名，完成後告訴我。

        [你在瀏覽器 UI 中選擇了 github.com, myapp.com]

你：    完成了

Claude: 已匯入 2 個域名 (47 個 Cookie)。會話已就緒。
```

或者完全跳過 UI：

```
你：   /setup-browser-cookies github.com

Claude: 已從 Comet 匯入 github.com 的 12 個 Cookie。
```

## `/codex`

這是我的 **第二意見模式**。

當 `/review` 從 Claude 的視角捕捉 Bug 時，`/codex` 帶來一個完全不同的 AI —— OpenAI 的 Codex CLI —— 來審核相同的差異。不同的訓練、不同的盲點、不同的長處。重疊部分告訴你什麼是絕對真實的。每個 AI 的獨特發現則是你能找到兩者單獨都無法捕捉到的 Bug 的地方。

### 三種模式

**審核 (Review)** — 針對當前差異執行 `codex review`。Codex 讀取每個變更的檔案，按嚴重程度對發現進行分類（P1 關鍵、P2 高、P3 中），並回傳 通過/失敗 裁決。任何 P1 發現 = 失敗。審核是完全獨立的 —— Codex 看不到 Claude 的審核。

**挑戰 (Challenge)** — 對抗模式。Codex 主動嘗試破壞你的代碼。它會尋找邊際情況、競態條件、安全漏洞以及在負載下會失敗的假設。使用最大推理能力 (`xhigh`)。將其視為對你邏輯的滲透測試。

**諮詢 (Consult)** — 具備會話連續性的開放對話。就代碼庫向 Codex 提問任何問題。後續問題會重複使用同一個會話，因此背景資訊會保留。非常適合「我這樣想對嗎？」這類時刻。

### 跨模型分析

當 `/review` (Claude) 和 `/codex` (OpenAI) 都審核了同一個分支時，你會得到一份跨模型比對：哪些發現是重疊的（高置信度）、哪些是 Codex 獨有的（不同視角），以及哪些是 Claude 獨有的。這就是代碼審核的「兩位醫生看同一位病人」的方法。

```
你：   /codex review

Claude: 正在執行獨立的 Codex 審核...

        CODEX 審核：通過 (3 項發現)
        [P2] 支付處理程序中的競態條件 — 並發扣款
             在無諮詢鎖的情況下可能導致雙重扣款
        [P3] 在 user.email 轉小寫前缺失 null 檢查
        [P3] Token 比較未使用恆定時間比較

        跨模型分析 (對比 /review)：
        重疊：支付處理程序中的競態條件 (兩者都捕捉到了)
        CODEX 獨有：Token 比較時序攻擊
        CLAUDE 獨有：列表照片中的 N+1 查詢
```

## 安全與護欄 (Safety & Guardrails)

四項技能為任何 Claude Code 會話增加安全軌道。它們透過 Claude Code 的 PreToolUse Hook 運作 —— 透明、會話範圍、無需配置檔案。

### `/careful`

當你在生產環境附近工作、執行破壞性指令，或只是想要個安全網時，說「be careful」或執行 `/careful`。每個 Bash 指令都會根據已知的危險模式進行檢查：

- `rm -rf` / `rm -r` — 遞迴刪除
- `DROP TABLE` / `DROP DATABASE` / `TRUNCATE` — 數據遺失
- `git push --force` / `git push -f` — 歷史紀錄重寫
- `git reset --hard` — 捨棄提交
- `git checkout .` / `git restore .` — 捨棄未提交的工作
- `kubectl delete` — 生產資源刪除
- `docker rm -f` / `docker system prune` — 容器/映像遺失

常見的建置產物清理（`rm -rf node_modules`, `dist`, `.next`, `__pycache__`, `build`, `coverage`）已被列入白名單 —— 對常規操作不會發出誤報。

你可以覆蓋任何警告。這些護欄是為了預防意外，而非存取控制。

### `/freeze`

限制所有檔案編輯僅限於一個目錄。當你正在除錯計費 Bug 時，你不希望 Claude 意外地「修復」 `src/auth/` 中無關的代碼。`/freeze src/billing` 會阻擋該路徑以外的所有編輯與寫入操作。

`/investigate` 會自動啟動此功能 —— 它偵測正在除錯的模組並凍結對該目錄的編輯。

```
你：   /freeze src/billing

Claude: 編輯已限制在 src/billing/。執行 /unfreeze 移除限制。

        [稍後，Claude 嘗試編輯 src/auth/middleware.ts]

Claude: 已阻擋 — 編輯超出了凍結邊界 (src/billing/)。
        跳過此變更。
```

注意：這僅阻擋 Edit 和 Write 工具。像 `sed` 這樣的 Bash 指令仍可以修改邊界外的檔案 —— 這是意外預防，而非安全沙箱。

### `/guard`

全面安全模式 —— 在一個指令中結合 `/careful` + `/freeze`。破壞性指令警告加上目錄範圍的編輯限制。用於接觸生產或除錯直播系統時。

### `/unfreeze`

移除 `/freeze` 邊界，再次允許隨處編輯。Hook 在會話中保持註冊 —— 它們只是允許所有操作。再次執行 `/freeze` 可設置新邊界。

## Greptile 整合

[Greptile](https://greptile.com) 是一間 YC 公司，可自動審核你的 PR。它能捕捉真實的 Bug —— 競態條件、安全問題，以及那些通過 CI 但在生產環境中爆炸的問題。它真的救過我好幾次。我超愛這群人。

### 設置

在 [greptile.com](https://greptile.com) 為你的 GitHub 倉庫安裝 Greptile —— 僅需約 30 秒。一旦它開始審核你的 PR，gstack 就會自動獲取它的評論。無需額外配置。

### 運作方式

任何自動化審核員的問題都在於分類 (triage)。Greptile 很棒，但並非每條評論都是真實問題。有些是誤判 (false positives)，有些則是針對你三次提交前就修復的內容。如果沒有分類層，評論會堆積如山，你就會開始忽視它們 —— 這違背了初衷。

gstack 解決了這個問題。`/review` 和 `/ship` 現在具備 Greptile 感知能力。它們讀取 Greptile 的評論，對每一條進行分類並採取行動：

- **有效問題**：加入關鍵發現，並在發布前修復。
- **已修復問題**：自動回覆並確認其發現。
- **誤判**：予以反駁 —— 你確認後，會發出一條回覆解釋為什麼它是錯的。

其結果是兩層式審核：Greptile 在 PR 上非同步捕捉問題，然後 `/review` 和 `/ship` 將這些發現作為正常工作流的一部分進行分類。沒有任何細節會遺漏。

### 從歷史中學習

你確認的每個誤判都會儲存到 `~/.gstack/greptile-history_zh_TW.md`。未來的執行會針對你的代碼庫自動跳過已知的誤判模式。此外，`/retro` 會追蹤 Greptile 隨時間變化的命中率 —— 這樣你就能看到信噪比是否在改善。

### 範例

```
你：   /ship

Claude: [同步 main, 執行測試, 交付前審核...]

        Greptile 在此 PR 上發現了 3 條評論：

        [有效] app/services/payment_service.rb:47 — 競態條件：
        並發扣款可能導致雙重扣款。建議在扣款代碼塊周圍增加
        資料庫級別的諮詢鎖。

        [已修復] app/models/user.rb:12 — 在轉小寫前缺失 email 
        的 null 檢查。
        → 已在提交 abc1234 中修復。正在自動回覆。

        [誤判] lib/auth.rb:88 — 「Token 比較應使用恆定時間比較。」
        我們在這裡已經使用了 ActiveSupport::SecurityUtils.secure_compare。

        正在修復 payment_service.rb 中的競態條件...

        身份驗證 Token 評論是誤判。
        選項：A) 回覆 Greptile 並解釋  B) 照樣修復  C) 忽視

你：    A

Claude: 已回覆 Greptile。所有測試通過。
        PR: github.com/you/app/pull/42
```

三條 Greptile 評論。一個真實修復。一個自動確認。一個回駁並回覆誤判。總共額外花費時間：約 30 秒。

# 交付前審核清單 (Pre-Landing Review Checklist)

## 指令

針對下述問題審核 `git diff origin/main` 的輸出內容。請務必具體 —— 引用 `檔案:行號` 並建議修復方案。跳過所有沒問題的內容，僅標記真實存在的問題。

**雙輪審核：**
- **第一輪 (關鍵)：** 首先執行 SQL 與數據安全、以及 LLM 輸出信任邊界檢查。此類別嚴重程度最高。
- **第二輪 (資訊)：** 執行其餘所有類別。嚴重程度較低，但仍需採取行動。

所有發現項均透過「優先修復審核 (Fix-First Review)」處理：明顯的機械式修復將自動執行，真正模糊的問題則會批次處理成一個用戶問題。

**輸出格式：**

```
交付前審核：N 個問題 (X 個關鍵, Y 個資訊)

**自動修復 (AUTO-FIXED)：**
- [檔案:行號] 問題 → 已套用修復

**需確認 (NEEDS INPUT)：**
- [檔案:行號] 問題描述
  建議修復：建議方案
```

若未發現問題：`交付前審核：未發現問題。`

簡明扼要。針對每個問題：一行描述問題，一行說明修復。無開場白，無摘要，不要說「整體看起來不錯」。

## 審核類別

### 第一輪 — 關鍵 (CRITICAL)

#### SQL 與數據安全
- SQL 中的字串插值（即使數值已執行 `.to_i`/`.to_f` —— 務必使用參數化查詢 (Rails: sanitize_sql_array/Arel; Node: prepared statements; Python: parameterized queries)）
- TOCTOU 競態條件：應使用原子化的 `WHERE` + `update_all` 模式替代「先檢查再設置」
- 繞過模型驗證進行直接資料庫寫入（Rails: update_column; Django: QuerySet.update(); Prisma: raw queries）
- N+1 查詢：在迴圈/視圖中使用的關聯缺失預先載入 (Rails: .includes(); SQLAlchemy: joinedload(); Prisma: include)

#### 競態條件與並發
- 「讀取-檢查-寫入」模式缺失唯一性約束，或未捕捉重複鍵錯誤並重試（例如：先執行 `where(hash:).first` 再執行 `save!`，卻未處理並發插入的情況）
- find-or-create 模式缺失資料庫唯一索引 —— 並發調用可能導致建立重複記錄
- 狀態轉移未使用原子化的 `WHERE old_status = ? UPDATE SET new_status` —— 並發更新可能導致轉移被跳過或重複套用
- 在用戶控制的數據上執行不安全的 HTML 渲染 (XSS)（Rails: .html_safe/raw(); React: dangerouslySetInnerHTML; Vue: v-html; Django: |safe/mark_safe）

#### LLM 輸出信任邊界
- LLM 生成的值（電子郵件、URL、姓名）在寫入資料庫或傳遞給郵件程式前未經格式驗證。持久化前應增加輕量級防護 (`EMAIL_REGEXP`, `URI.parse`, `.strip`)。
- 結構化工具輸出（陣列、雜湊）在寫入資料庫前未經類型/結構檢查即被接受。

#### 列舉 (Enum) 與值完整性
當差異引入了新的列舉值、狀態字串、等級名稱或類型常量時：
- **追蹤每個消費者**：閱讀（不只是 grep —— 務必「閱讀」）每個對該值進行 switch、過濾或顯示的檔案。若有任何消費者未處理新值，請標記。常見遺漏：在前端下拉選單增加了值，但後端模型/計算方法卻未將其持久化。
- **檢查允許列表/過濾陣列**：搜尋包含同類值的陣列或 `%w[]` 列表（例如：若在等級中增加了 "revise"，尋找所有的 `%w[quick lfg mega]` 並驗證是否在需要處包含了 "revise"）。
- **檢查 `case`/`if-elsif` 鏈**：若既有代碼針對該列舉進行分支處理，新值是否會落入錯誤的預設分支？
執行方法：使用 Grep 尋找所有對同類值的引用（例如：grep "lfg" 或 "mega" 以尋找所有等級消費者）。閱讀每個匹配項。此步驟需要閱讀差異「之外」的代碼。

### 第二輪 — 資訊 (INFORMATIONAL)

#### 具備條件的副作用
- 程式碼路徑根據條件分支，卻在其中一個分支忘記套用副作用。範例：項目被提升為已驗證，但僅在次要條件為真時才附加 URL —— 另一個分支在無 URL 的情況下提升，導致記錄不一致。
- 日誌訊息宣稱某個動作已發生，但該動作卻在特定條件下被跳過。日誌應準確反映實際發生的情況。

#### 魔術數字與字串耦合
- 在多個檔案中使用裸數字字面量 —— 應使用具名常量並集中記錄文件。
- 錯誤訊息字串在別處被用作查詢過濾器（grep 該字串 —— 是否有任何內容以此進行匹配？）。

#### 死代碼與一致性
- 變數已賦值但從未被讀取。
- PR 標題與 VERSION/CHANGELOG 檔案間的版本不匹配。
- 更新日誌 (CHANGELOG) 條目描述不準確（例如：「將 X 變更為 Y」，但 X 根本從未存在過）。
- 程式碼變更後，註釋/文件字串 (docstrings) 仍描述舊行為。

#### LLM 提示詞問題
- 提示詞中使用 0 起始的列表（LLM 通常回傳 1 起始的內容）。
- 提示詞文本中列出的可用工具/能力與 `tool_classes`/`tools` 陣列中實際掛載的內容不符。
- 在多處聲明了單字/Token 限制，可能導致同步偏差。

#### 測試缺口
- 負向路徑測試僅斷言類型/狀態，卻未檢查副作用（URL 是否附加？欄位是否填寫？回呼是否觸發？）。
- 針對字串內容的斷言未檢查格式（例如：斷言標題存在卻未檢查 URL 格式）。
- 當程式碼路徑明確「不應」調用外部服務時，缺失 `.expects(:something).never`。
- 安全執行功能（阻擋、速率限制、身份驗證）缺失驗證執行路徑端到端運作的整合測試。

#### 完整性缺口
- 完整版本成本低於 30 分鐘 CC 時間的捷徑實作（例如：部分列舉處理、不完整的錯誤路徑、易於增加的缺失邊際情況）。
- 呈現選項時僅提供人類團隊的工作量估算 —— 應同時顯示人類與 CC+gstack 的時間。
- 測試覆蓋缺口，且增加缺失測試屬於「湖泊」而非「海洋」（例如：缺失負向路徑測試、缺失與正常路徑結構對應的邊際情況測試）。
- 功能僅實作了 80-90%，但在增加少量代碼即可達成 100% 的情況下。

#### 加密與熵 (Entropy)
- 截斷數據而非哈希化（取最後 N 個字元而非 SHA-256） —— 熵較低，易發生碰撞。
- 在安全性敏感的值上使用 `rand()` / `Random.rand` —— 應改用 `SecureRandom`。
- 在秘密或 Token 上執行非恆定時間比較 (`==`) —— 易受時序攻擊。

#### 時間窗安全性
- 日期鍵查找假設「今天」涵蓋 24 小時 —— 太平洋時間早上 8 點的報告在今天的鍵下僅能看到午夜到早上 8 點的數據。
- 相關功能間的時間窗不匹配 —— 一個針對相同數據使用每小時桶位，另一個則使用每日鍵。

#### 邊界處的類型轉換
- 數值跨越 Ruby → JSON → JS 邊界時類型可能發生變化（數字 vs 字串） —— 哈希/摘要輸入必須規範化類型。
- 哈希/摘要輸入在序列化前未調用 `.to_s` 或等效方法 —— `{ cores: 8 }` 與 `{ cores: "8" }` 會產出不同的哈希值。

#### 視圖/前端
- 在局部視圖 (partials) 中內聯 `<style>` 區塊（每次渲染都會重新解析）。
- 在視圖中執行 O(n*m) 查找（在迴圈中使用 `Array#find` 而非 `index_by` 雜湊）。
- 在 Ruby 端對資料庫結果執行 `.select{}` 過濾，而這本可以是一個 `WHERE` 子句（除非是有意避免前導通配符的 `LIKE`）。

## 嚴重程度分類

```
關鍵 (CRITICAL) (最高嚴重程度)：    資訊 (INFORMATIONAL) (較低嚴重程度)：
├─ SQL 與數據安全                  ├─ 具備條件的副作用
├─ 競態條件與並發                  ├─ 魔術數字與字串耦合
├─ LLM 輸出信任邊界                ├─ 死代碼與一致性
└─ 列舉與值完整性                  ├─ LLM 提示詞問題
                                   ├─ 測試缺口
                                   ├─ 完整性缺口
                                   ├─ 加密與熵
                                   ├─ 時間窗安全性
                                   ├─ 邊界處的類型轉換
                                   └─ 視圖/前端

所有發現項均透過「優先修復審核」處理。嚴重程度決定了呈現順序以及
「自動修復」對比「詢問」的歸類 —— 關鍵發現傾向於「詢問」（風險較高），
資訊性發現傾向於「自動修復」（較具機械性）。
```

## 優先修復啟發式 (Fix-First Heuristic)

此啟發式方法由 `/review` 與 `/ship` 共同引用。它決定了代理是自動修復發現項還是詢問用戶。

```
自動修復 (由代理直接修復)：         詢問 (需要人工判斷)：
├─ 死代碼 / 未使用的變數           ├─ 安全性 (身份驗證, XSS, 注入)
├─ N+1 查詢 (缺失預先載入)         ├─ 競態條件
├─ 與程式碼矛盾的過時註釋          ├─ 設計決策
├─ 魔術數字 → 具名常量             ├─ 大型修復 (>20 行)
├─ 缺失的 LLM 輸出驗證             ├─ 列舉完整性
├─ 版本/路徑不匹配                 ├─ 移除功能
├─ 變數已賦值但未讀取              └─ 任何會改變用戶可見行為的
└─ 內聯樣式, O(n*m) 視圖查找          變更
```

**判斷準則**：若修復是機械性的，且資深工程師會在不經討論的情況下直接套用，則為「自動修復」。若合理的工程師可能對修復方案有不同意見，則為「詢問」。

**關鍵發現預設為「詢問」**（本質上風險較高）。
**資訊性發現預設為「自動修復」**（較具機械性）。

## 抑制項 — 絕不標記這些

- 「X 與 Y 冗餘」，且該冗餘無害並有助於可讀性時（例如：`present?` 與 `length > 20` 冗餘）。
- 「增加註釋解釋為什麼選擇此閾值/常量」 —— 閾值在調優期間會變動，註釋會過時。
- 「此斷言可以更嚴密」，且該斷言已涵蓋了行為時。
- 建議僅為了「一致性」而做的變更（例如：將一個值封裝在條件句中，僅為了匹配另一個常量的防護方式）。
- 「正則表達式未處理邊際情況 X」，且輸入受限且 X 在實踐中絕不會發生時。
- 「測試同時執行了多個防護」 —— 沒問題，測試不需要隔離每個防護。
- 評估閾值的變更 (max_actionable, min scores) —— 這些是根據經驗調優的且經常變動。
- 無害的空操作 (no-ops)（例如：對一個絕不會在陣列中的元素執行 `.reject`）。
- 您正在審核的差異中「已經處理過」的任何內容 —— 在發表評論前請先閱讀「完整」的差異內容。
